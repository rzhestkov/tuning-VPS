# VPS Setup Scripts

## Post-Run Чеклист

После завершения полезно отдельно проверить ключевые сервисы и конфиги:

```bash
# SSH
sudo sshd -t
sudo systemctl status ssh
sudo ss -tlnp | grep ssh

# Firewall
sudo ufw status verbose

# Fail2ban
sudo systemctl status fail2ban
sudo fail2ban-client status sshd

# Auditd
sudo systemctl status auditd
sudo auditctl -l | grep sshd_config

# Автообновления
systemctl list-timers apt-daily.timer apt-daily-upgrade.timer
sudo grep -E "Allowed-Origins|Automatic-Reboot" /etc/apt/apt.conf.d/50unattended-upgrades

# Needrestart
sudo grep "nrconf{restart}" /etc/needrestart/needrestart.conf

# Journald
sudo systemctl status systemd-journald
sudo journalctl --disk-usage
sudo grep -E "^(Storage|SystemMaxUse)" /etc/systemd/journald.conf

# Logrotate
sudo logrotate -d /etc/logrotate.d/custom-system

# Docker и MTProto
docker ps
docker logs --tail 50 mtproto-proxy
```

Автоматическая настройка свежих VPS-серверов с защитой от блокировки. 
Скрипты настраивают SSH, файрвол, Docker и автоматические обновления.

## ⚡ Быстрый старт (Ubuntu 24.04)

1. Подключитесь к серверу как root. На своем компьютере:
   
   ```bash
   ssh root@YOUR_SERVER_IP
   ```

2. Скачайте скрипт. На сервере после подключения:
   
   ```bash
   curl -fsSL https://raw.githubusercontent.com/rzhestkov/tuning-VPS/main/setup_ubuntu_24.04.sh -o setup.sh
   ```

3. Запустите
   
   ```bash
   sudo bash setup.sh
   ```

## 🔑 Подготовка перед первым запуском

### 1. Поместите SSH ключ в репозиторий

В папке `ssh` должен лежать готовый файл `authorized_keys`, содержащий только ключи типа `ssh-ed25519`. Любые активные строки с RSA, ECDSA или другими типами ключей остановят скрипт до изменения SSH-конфигурации.

## 2. Настройте переменные в скрипте

Убедитесь, что в `setup_ubuntu_24.04.sh` верно прописаны:

```bash
GITHUB_USER="YOUR_GITHUB_USERNAME"  # Ваш аккаунт на GitHub
REPO_NAME="vps-setup"               # Название этого репозитория
NEW_USER="user1"                    # Имя нового пользователя (можно оставить)
SSH_PORT="2332"                     # Порт для SSH (можно изменить)
```

## 🚀 Детальная инструкция

### Шаг 1: Первое подключение

Подключитесь к свежему VPS по SSH как `root` через порт `22`. Для повторного запуска на уже защищённом сервере входите как `user1` на порту `2332`. Скрипт определяет фактически слушающие IPv4-порты и эффективную политику SSH до обновления пакетов.

### Шаг 2: Запуск скрипта

```bash
# Скачивание
curl -fsSL https://raw.githubusercontent.com/USERNAME/REPO/main/setup_ubuntu_24.04.sh -o setup.sh

# Просмотр (опционально, но рекомендуется)
cat setup.sh | less

# Запуск
chmod +x setup.sh
sudo ./setup.sh
```

### Шаг 3: Контрольная проверка (ВАЖНО!)

**Не закрывайте текущее окно терминала, открытое под root!**

Откройте **новое окно** на вашем компьютере c авторизацией по ssh-ключу на порту 2332 и проверьте подключение:

```bash
ssh -4 -p 2332 user1@SERVER_IP
```

Проверьте вход и `sudo -n true`, затем ответьте `y`, `Y` или `yes`. После применения финальной политики скрипт попросит проверить вход ещё раз в новом окне. При отказе или ошибке восстанавливается исходное состояние SSH, ключей и UFW; дальнейшие блоки не запускаются.

Скрипт читает подтверждение из `/dev/tty`. Без интерактивного терминала переход останавливается и откатывается. На повторном запуске без изменений SSH и ключей подтверждение не требуется.

### Выбор MTProto Proxy

После проверки Docker скрипт сначала спрашивает, нужно ли устанавливать сервис MTProto. При согласии предлагается единый выбор:

1. MTProto от 9seconds [9seconds/mtg](https://github.com/9seconds/mtg)
2. MTProto от seriyps [seriyps/mtproto_proxy](https://github.com/seriyps/mtproto_proxy)
3. Отказаться

Одновременно устанавливается не более одной реализации.

Для выбранного прокси потребуется указать SNI — доступный HTTPS-домен, характерный для страны размещения VPS. Вводите только доменное имя без `https://`, порта и пути. Оба варианта используют порт `443` и единое имя контейнера `mtproto-proxy`; установка выбранного варианта заменяет ранее созданный этим скриптом контейнер.

### Проверки перед запуском

Скрипт проверяет:

- **Пользователь** — если `user1` уже существует, создание пропускается
- **SSH ключи** — скачанный и прежний наборы должны содержать действительные активные `ssh-ed25519`; прежние ключи сохраняются до проверки нового входа
- **Порт SSH** — допускаются исходное состояние с 22 и уже защищённое состояние с 2332; потерянный при `sudo`/`su` `SSH_CONNECTION` дополняется проверкой родительского сокета
- **SSH-конфигурация** — оба кандидата проходят `sshd -t` и `sshd -T -C`; конфликт с провайдерскими `Include`/`Match` останавливает переход без отключения чужих файлов
- **UFW** — включает IPv4 firewall с deny incoming и добавляет только SSH 2332/tcp; уже существующие allow-правила не удаляет
- **Docker** — пропускает установку, если Docker уже есть; остановленный daemon автоматически не запускает

### Политика UFW и Docker

Базовый скрипт открывает только IPv4-порт SSH 2332/tcp. Он не открывает 80, 443, VPN-порты и порты приложений. Их должен открывать отдельный модуль приложения вместе с проверкой конкретного сервиса.

В текущей версии ниже по сценарию ещё остаётся устаревший опциональный MTProto-блок, который сам публикует 443. Он будет удалён в Milestone 7; до этого не включайте его, если нужен только базовый VPS.

Если на сервере уже есть разрешающие правила UFW, скрипт сохраняет их и показывает в итоговом отчёте. В частности, правило 22/tcp, созданное хостером или ранее вручную, не удаляется автоматически; после перехода на 2332 SSH на 22 уже не слушает, но правило следует отдельно проверить и убрать вручную, если оно больше не нужно.

Docker может публиковать порты через свой firewall backend, поэтому опубликованный контейнерный порт может быть доступен извне независимо от правил UFW. Скрипт показывает такие контейнеры и порты без вывода журналов и секретов. Для новых приложений предпочитайте привязку к 127.0.0.1 либо явно задавайте политику в цепочке DOCKER-USER; после публикации порта всегда проверяйте доступ с другой машины.

## ⚠️ Безопасность и защита от блокировки

### Почему вы не потеряете доступ:

1. **Два контрольных входа**: до первого сохраняется старый SSH-доступ; второй проверяет финальную политику и точный набор ключей.
2. **Проверка кандидатов**: до изменения доступа выполняются `sshd -t` и `sshd -T -C`; после перезапуска проверяются реальные IPv4 listener.
3. **Отдельный управляемый файл**: проект пишет `/etc/ssh/tuning-vps.conf` и добавляет одну строку `Include` в начало основного конфига, сохраняя провайдерские дополнения.
4. **Откат**: при ошибке восстанавливаются сохранённые в защищённом временном каталоге исходные SSH-файлы, ключи, состояние root, UFW и systemd; доступ на исходном порту проверяется. Если проверка отката не прошла, каталог сохраняется для rescue-консоли.

До ручного подтверждения контрольного входа скрипт временно сохраняет порт 22 и прямой вход `root`. После подтверждения прямой вход под `root` отключается через `PermitRootLogin no`, а пароль root блокируется командой `passwd -l root`. Учётная запись root не удаляется: административная оболочка доступна через `sudo -i`.

> **Важно:** если единственный приватный ключ `user1` будет утерян и не останется активной SSH-сессии, сервер потребуется полностью пересоздать. Не рассчитывайте на вход через root как на способ восстановления доступа.

### Если всё же потеряли доступ:

Через rescue-режим или консоль восстановления хостинга проверьте вывод ошибочного запуска. Если скрипт сообщил путь каталога `/etc/ssh/.tuning-vps.*`, в нём сохранены исходные файлы для восстановления. Не копируйте произвольный `sshd_config.bak.*`: он может относиться к другому запуску. После восстановления проверьте `sshd -t`, состояние `ssh.service`/`ssh.socket` и правила UFW.

```bash
sudo sshd -t
sudo systemctl status ssh.service ssh.socket
sudo ufw status verbose
```

## 🔍 Диагностика после установки

Скрипт выводит отчёт в конце, но вы можете проверить вручную:

```bash
# Проверка SSH
sudo systemctl status ssh
sudo ss -tlnp | grep ssh

# Проверка файрвола
sudo ufw status verbose

# Проверка Docker
docker --version
sudo -u user1 docker ps
docker ps --format 'table {{.Names}}\t{{.Ports}}'

# Проверка автоматических обновлений
systemctl list-timers apt-daily-upgrade.timer
cat /var/log/unattended-upgrades/unattended-upgrades.log | tail -5

# Проверка временной зоны и времени
timedatectl
timedatectl status | grep "System clock synchronized"

# Проверка systemd-timesyncd
sudo systemctl status systemd-timesyncd

# Проверка journald (системный журнал)
sudo journalctl --disk-usage
sudo systemctl status systemd-journald

# Проверка logrotate
sudo logrotate -d /etc/logrotate.d/custom-system

# Проверка fail2ban
sudo systemctl status fail2ban
sudo fail2ban-client status sshd

# Проверка предустановленных пакетов (что делает скрипт автоматически)
python3 --version
docker --version
nginx -v
mysql --version
redis-server --version
```

## 🐛 Troubleshooting

### "Настройки SSH отличаются от основного конфига"

**Причина**: провайдерский `Include`, `ssh.socket` или параметры запуска сервиса.
**Решение**: проверьте фактически применённые параметры и активные дополнения:

```bash
sudo sshd -T
sudo grep -nE '^[[:space:]]*(Include|Port|PasswordAuthentication|PermitRootLogin)' /etc/ssh/sshd_config
sudo systemctl cat ssh.service ssh.socket
```

### "UFW блокирует соединение"

```bash
# Из действующей сессии проверьте правило и добавьте доступ для своего IPv4.
sudo ufw status verbose
sudo ufw allow from YOUR_IPV4 to any port 2332 proto tcp
```

### "Docker не доступен пользователю"

```bash
# Перелогиниться или выполнить:
sudo usermod -aG docker $USER
newgrp docker
```

## 📝 Лог изменений

- **v1.6** - Усилены проверки, повторный запуск и практичность конфигурации
  
  - **Post-check после секций**: добавлены дополнительные проверки результата настройки для services, limits, user/sudo, SSH keys, fail2ban, auditd, unattended-upgrades, needrestart, journald и MOTD
  - **Повторный запуск**: улучшена диагностика для rerun-сценария и добавлен отдельный post-run чеклист в README
  - **SSH keys**: скрипт теперь останавливается до SSH hardening, если `authorized_keys` пустой или не содержит валидный публичный ключ
  - **Rollback SSH**: при ошибке восстанавливаются исходный `sshd_config`, состояние пароля root, порт 22 и правило UFW
  - **SSH hardening**: убраны слишком жёсткие ручные crypto-ограничения, оставлены более совместимые и практичные настройки
  - **Limits**: управляемая секция размещена в основном `limits.conf`, проверяются реальные лимиты login-сессии `user1`
  - **Auditd**: проверки правил усилены, а набор syscall-правил сделан более практичным для VPS
  - **Автообновления, needrestart и journald**: основные конфиги проверяются семантически, ошибочные изменения откатываются
  - **MOTD**: статическое сообщение действительно подключается через PAM, динамический MOTD отключается
  - **Docker и MTProto**: добавлены явные состояния, безопасный отчёт и единый выбор одной из двух реализаций MTProto

  - **Отключение сервисов**: snapd, apport, whoopsie, lxd, udisks2

  - **Needrestart**: Автоматический перезапуск сервисов

  - **Обновлена нумерация секций**: 01-22 в соответствии с порядком выполнения

  - **Временная зона**: Установка Europe/Berlin через timedatectl
